# 另一台 Mac 的验收清单

目标是分别验证：代码能在另一台机器启动、不同入口使用同一套任务、独立执行器能被替换。不要把“进程被找到”当成“已经能完成工作”。

## 1. 干净启动

从 GitHub 克隆仓库，在仓库目录运行：

```sh
python3 --version
./task-workbench doctor
./task-workbench start
```

打开 <http://127.0.0.1:8766/>。预期：

- 只有一个初始项目“建立一个任务管理器”，没有开发机的私有任务历史。
- 初始项目路径指向这台 Mac 的克隆目录。
- 新建任务后刷新页面仍然存在。
- 停止并重新启动服务后，项目和任务仍在。

若端口已被其他服务使用，使用 `./task-workbench start --port 8767`，打开对应地址；CLI/MCP 连接也需改为相同端口。

## 2. 不用模型的协议检查

```sh
python3 examples/check_custom_agent.py
```

预期输出明确的通过结果。这个检查会启动独立的示例进程，验证执行、产物、会话恢复和取消，不依赖 Codex / Claude 的账号。

在网页里选择演示 Agent 的方式见 [示例说明](../examples/README.md)。它只验证接口，不是真正的 coding agent。

## 3. Claude Code 的实际能力

先在终端正常启动 Claude Code，确认已登录且能完成一个普通请求，再回到工作台。新建一个仅用于试用的项目文件夹，避免使用重要项目。

在网页选择 Claude Code，新建如下目标并先生成计划：

> 在这个试用项目里创建 hello.txt，内容为 task-workbench-ok，末尾加一个换行。只需要一个子任务。完成后给出验证结果。

依次核验：

- 计划能返回并进入“待你处理”。
- 点击批准后出现子任务，显示运行日志。
- 子任务生成正确文件并进入待验收。
- 给反馈“把文件内容改成 task-workbench-revised，保持末尾换行”，任务能够继续，执行轮次增加。
- 验收子任务后，父任务完成。
- 文件或命令权限被 CLI 拒绝时，工作台显示原因；不把拒绝当作成功。

另外创建一个可安全中断的试用任务，运行中取消。预期先显示“正在停止”，退出后显示“已取消”，随后可重试。

这组检查需要真实模型调用，使用目标设备上 Claude 的正常额度。开发机未登录 Claude，不能替这台设备宣称已经通过。

## 4. 换成 Codex 或其他 Agent

使用相同的试用目标，选择 Codex。换 Agent 后，任务、反馈、验收和产物操作方式应保持一致。

其他 coding agent 请按 [适配协议](ADAPTERS.md)接入。最少验证：

- 独立进程确实收到 stdin 中的目标。
- 工作目录是所选项目目录。
- 结果、错误、日志和产物被正确识别。
- 若支持会话恢复，反馈使用本次任务的会话；不混用其他任务或 provider 的会话。
- 取消后不留下仍在工作的子进程。

## 5. 从 CLI 和 MCP 看同一份数据

```sh
./task-workbench projects
./task-workbench tasks
```

结果应与网页一致。按 README 配置 MCP 后，在相应 Agent 里要求调用 `list_projects` / `list_tasks`，核对同样的项目和任务；再通过 `create_task` 创建一个不自动开始的任务，确认它出现在网页里。

若配置了其他端口，MCP 入口参数应为：

```json
["--url", "http://127.0.0.1:8767", "mcp"]
```

## 记录试用结果

可在 GitHub issue 或当前对话提供：macOS / Python / Agent CLI 版本、执行器名称、卡在哪一步、错误文字，以及任务的执行日志。不要附带密码、访问令牌或完整认证文件。

跨设备复制任务历史、自动同步、多 worker 的 Git worktree 隔离和自动合并，尚未包含在第一版中。
